## F1 로그인 / 계정 모델 (확정, 2026-09-03)

- 로그인 아이디 = 사번 (EMP-001 형식). 시드에 있는 유일한 식별자이며 동명이인을 자연스럽게 구분.
- 초기 비밀번호 = 관리자가 계정 생성 시 자동 발급된 임시 비밀번호를 전달. 첫 로그인 시 변경 강제.
  근거: 관리자가 직원의 개인 비밀번호를 알 필요가 없음.
- 관리자 = 직원 테이블의 한 레코드 + Role 컬럼(ADMIN / EMPLOYEE). 별도 관리자 테이블 없음.
  관리자는 전 직원 정보 조회·수정, 퇴사 처리, Background Check 수행 가능.
- 로그인 화면은 하나. 로그인 후 DB의 Role을 읽어 화면 분기 (ADMIN → 대시보드, EMPLOYEE → 내 정보).
- "삭제"는 물리 삭제가 아닌 퇴사 처리(상태 변경)로 해석. (F6에서 상세 논의)

## F2 / F3 / F4 직원 정보 모델 (확정, 2026-09-03)

| 주소 | O | O | O / O | |

### 수정 절차 (미정 항목 4)
- 직원의 연락처·주소 수정은 즉시 반영. 변경 이력(누가, 언제, 어떤 항목을, 이전값→이후값) 저장.
- 성명·생년월일·부서·직급·입사일은 관리자만 수정. 성명·생년월일은 Background Check 입력값이므로 직원 임의 변경 불가.

### 성명 저장
- 성명은 통째로 저장(시드 그대로). 계정 생성 시 백엔드에서 복성 사전 기반으로 lastName/firstName을 파싱해 별도 컬럼에 저장.
- 파싱 모호 케이스(선우진 등) 처리 방식은 F4에서 결정.

## F4 계정 생성 / F5 목록·상세 (확정, 2026-09-03)

- 사번 자동 채번: 마지막 사번 + 1 (시드 EMP-010 다음은 EMP-011). 퇴사자 번호 재사용 없음.
- 성명 파싱 규칙: 첫 글자 = lastName, 나머지 = firstName. 복성 사전 없음.
  근거: 실제 성씨 관리가 목적이 아니라 외부 API(firstName/lastName) 입력 형식을 맞추는 것이 우선.
  결과 예: 남궁서준 → 남 / 궁서준, 황보라온 → 황 / 보라온, 선우진 → 선 / 우진, 김솔 → 김 / 솔.
  (DECISIONS 재료: 반대로 복성 사전을 두면 실제 성씨에 가까워지지만 선우진 같은 모호 케이스는 여전히 못 가르고 사전 유지 비용이 생김)
- 생년월일은 선택 입력. 없으면 계정 생성은 허용하되 Background Check 요청 버튼을 비활성화하고 사유를 표시.
  (시드 EMP-007 이서연이 이 경우. 외부 API는 dateOfBirth 필수 → 실측에서 400 확인)
- 계정 생성 입력: 성명, 생년월일(선택), 연락처, 주소, 부서, 직급, 입사일, Role. 생성 직후 임시 비밀번호를 관리자 화면에 1회 표시.
- 직원 목록: 기본으로 전체(재직+퇴사) 표시, 재직 상태 필터 제공. 상태 배지로 구분.
- 상세 화면(관리자): 전체 항목 + 퇴사일 + Background Check 이력/최근 상태.

## F6 퇴사 처리 (확정, 2026-09-03) — 미정 항목 (1)

- 관리자가 퇴사 처리 버튼을 누르면 즉시 재직상태=퇴사. 퇴사일은 기록용으로 저장(기본값 처리 당일).
- 퇴사 처리 시 해당 직원의 서버 세션을 즉시 삭제. 다음 요청부터 차단.
  → 비기능 함의: 서버 측 세션 저장소가 필요 (무상태 JWT만으로는 즉시 무효화 불가).
- 물리 삭제 없음. 퇴사자 레코드와 Background Check 이력은 유지(F8에서 보관 기간 결정).

## F7 Background Check 요청 (확정, 2026-09-03) — 미정 항목 (2)

- 실행 시점: 관리자가 직원 상세 화면에서 버튼을 눌러 수동 실행. 계정 생성과 분리.
- 재실행: 이전 건이 완료(clear/flagged)된 뒤에만 허용. pending 중에는 버튼 비활성화. 이력은 누적.
  근거: 실측상 같은 employeeId로 POST하면 매번 새 checkId가 생기므로 중복 요청을 앱에서 막아야 함.
- 생년월일 없는 직원은 버튼 비활성화 + 사유 표시 (F4 참조).
- API 입력값: employeeId=사번, lastName/firstName=파싱 컬럼, dateOfBirth=생년월일.
- pending 처리(폴링 주기·타임아웃·재시도)는 MEASUREMENTS.md 실측값으로 결정.

## F8 Background Check 결과 조회·보관 (확정, 2026-09-03) — 미정 항목 (3)

- 보관: 재직 중에는 이력 전부 보관. 퇴사 처리 시 해당 직원의 Background Check 결과 삭제.
  (가정: 퇴사 처리 트랜잭션 안에서 결과 레코드를 삭제하고, "삭제했다"는 사실만 감사 로그에 남김. 유예 기간 없음 — 확인 필요)
- 열람: 관리자만. 결과 상세를 열람할 때마다 감사 로그(누가, 언제, 어느 직원의 어느 checkId를) 기록.
- 직원 본인은 자기 결과를 볼 수 없음. 조회 여부도 노출하지 않음.
- 화면: 직원 상세에 이력 목록(checkId, 요청일, status). 상세 펼치기 시 criminalRecord·educationVerified·employmentVerified·creditScore 표시 + 감사 로그 기록.

## F9 접근 권한 통제 (확정, 2026-09-03)

- 역할: ADMIN / EMPLOYEE (직원 테이블 Role 컬럼).
- EMPLOYEE: 자기 레코드만 조회, 연락처·주소만 수정. 다른 사번 접근 시 403.
- ADMIN: 전 직원 조회·수정, 계정 생성, 퇴사 처리, Background Check 요청·열람.
- 퇴사자: 로그인 자체 거부(안내 문구 표시). API 레벨에서도 재직상태 검사. 기존 세션은 퇴사 처리 시 삭제(F6).
- 권한 검사는 화면 분기가 아니라 서버(API)에서 수행. 화면 분기는 편의용.

## 감사 로그 대상 (기능 논의에서 도출)
- 직원 정보 변경 이력 (F3): 누가, 언제, 어떤 항목, 이전값 → 이후값
- Background Check 상세 열람 (F8)
- Background Check 결과 삭제 (F8, 퇴사 처리 시)
- 퇴사 처리 (F6)

## 비기능 요구사항 논의 예정 항목
- 인증 방식: 서버 세션 저장소 필요(F6 즉시 무효화). 세션 만료 시간, 쿠키 속성.
- 비밀번호: 해시 알고리즘, 임시 비밀번호 생성 규칙, 첫 로그인 변경 강제 흐름.
- 외부 API 장애 처리: 타임아웃·재시도·폴링 (MEASUREMENTS 실측값 기반), 실패 시 화면 표시.
- 감사 로그 저장 구조와 열람 화면 여부.
- 배포 환경, DB 선택, 시크릿 관리, HTTPS.
- 민감정보 저장 방식(암호화 여부), 로그에 민감정보 미기록.

## F0 시드 데이터 적재 (확정, 2026-09-03)
- 시드 10명은 목록 그대로 적재. 성명 통째 저장 + 파싱 규칙(첫 글자=성)으로 firstName/lastName 채움. EMP-007 생년월일 null.
- 관리자 계정 사번 = ADMIN-001. EMP- 채번 규칙(마지막+1)은 EMP- 접두어 안에서만 적용되며 ADMIN- 계정은 시드로만 생성.
- 연락처·주소·부서·직급·입사일은 시드에 없으므로 임의값으로 채움(시드 표 항목은 수정하지 않음).

# 비기능 요구사항 논의 기록

## N1 인증 · 세션 (확정, 2026-09-03)

- 세션 저장: 서버 세션 테이블(RDB). 서버가 늘어나면 Redis 같은 외부 저장소로 일원화(구조는 세션 저장소 인터페이스로 분리).
- 전달: 세션 ID를 HttpOnly 쿠키로. JS 접근 불가. (Secure, SameSite 속성은 N5 배포에서 확정)
- 만료: 미사용 30분. 사용 중에는 요청마다 연장(슬라이딩).
- 퇴사 처리 시 해당 사번의 세션 행 삭제 → 다음 요청부터 401.
- 비밀번호: 최소 8자, 숫자·특수문자 포함. 임시 비밀번호와 동일 불가. 해시는 bcrypt 또는 argon2.
- 첫 로그인(임시 비밀번호 상태)은 비밀번호 변경 화면 외 접근 불가.
- 로그인 실패: 사번이 EMP-NNN 패턴이라 추측 가능 → 무차별 대입 방어 필요. 연속 실패 N회 초과 시 계정 잠금 후 비밀번호 변경 유도.
  (가정: N=5. 잠금 해제 방법은 N2에서 결정)

## N2 계정 보호 (확정, 2026-09-03)

- 연속 로그인 실패 5회(가정) 초과 시 잠금. 잠금 해제는 관리자가 임시 비밀번호를 재발급해야만 가능.
  재발급 시 잠금 해제 + 첫 로그인 비밀번호 변경 강제 흐름으로 합류(계정 생성 시 임시 비밀번호 로직 재사용).
- 자동 해제 없음.

## N3 외부 API(Background Check) 장애 처리 (확정, 2026-09-03)

- 요청 흐름: 관리자 버튼 → 서버가 POST → 응답을 DB에 저장(checkId, status) → pending이면 서버 내부 작업이 GET 폴링해 DB 갱신.
  화면은 DB 상태를 주기적으로 조회(외부 API를 브라우저가 직접/중계 호출하지 않음).
- 실패(재시도 소진, 4xx/5xx 확정, 타임아웃)도 이력 행으로 남김: 상태 FAILED/TIMEOUT + 사유(HTTP 코드/에러). 재실행 조건에서 실패 건은 완료로 간주.
- POST 성공 후 폴링 상한까지 pending이면 상태 TIMEOUT으로 표시하고 "결과 다시 확인" 버튼 제공 → checkId로 GET만 재조회(POST 중복 없음).
- 타임아웃·재시도 횟수/간격·폴링 주기·중단 조건의 구체 값은 MEASUREMENTS.md 실측값으로 결정.

## N4 민감정보 · 감사 로그 (확정, 2026-09-03)

- Background Check 상세 필드는 DB 평문 저장. 저장소 암호화(RDS at-rest)에 의존. 앱 로그·감사 로그에는 값 미기록(checkId·status만).
- 보유 기간 통제는 퇴사 시 삭제(F8)로.
- 감사 로그 화면: 직원 상세 화면의 "이력" 탭. 해당 직원에 대한 정보 변경·결과 열람·결과 삭제·퇴사 처리 기록 표시. 별도 전역 페이지 없음.

## N5 스택 · 배포 (확정, 2026-09-03)

- 프론트: Next.js → 정적 빌드 → Cloudflare Pages.
- 백엔드: Spring Boot → EC2. 세션 테이블·백그라운드 폴링(@Scheduled)·트랜잭션은 여기서.
- DB: RDS PostgreSQL. 외부 API와 같은 ap-northeast-2 리전이면 지연 측정값 비교 근거가 됨.
- 파생 제약 (구현 시 확정 필요):
  - 프론트(Cloudflare)와 API(EC2)가 다른 오리진 → 세션 쿠키가 cross-site. 
    선택지 A: 같은 도메인의 서브도메인(app.xxx / api.xxx)으로 묶어 SameSite=Lax 유지 (도메인 필요).
    선택지 B: 별개 도메인 + SameSite=None; Secure + CORS credentials 허용.
    → 도메인 보유 여부 확인 필요.
  - EC2에 HTTPS 필수(Secure 쿠키). 도메인 + 인증서(Let's Encrypt 또는 ALB+ACM).
  - Next.js 정적 빌드이므로 SSR 없음. 권한 분기는 API 응답 기반, 실제 통제는 Spring Security에서.
  - 시크릿(DB 비밀번호, 외부 API URL)은 환경변수/Parameter Store. 저장소에 커밋 금지.

## 비기능 요약 표

| 영역 | 결정 |
|---|---|
| 인증 | 서버 세션 테이블(RDB) + HttpOnly 쿠키, 미사용 30분 만료, 사용 중 연장 |
| 퇴사 통제 | 세션 행 즉시 삭제 + 로그인 거부 + API 재직상태 검사 |
| 비밀번호 | 8자 이상, 숫자·특수문자 포함, 임시와 다르게, bcrypt/argon2 |
| 잠금 | 연속 실패 5회 → 잠금, 관리자 임시 비밀번호 재발급으로만 해제 |
| 외부 API | 서버가 POST + 백그라운드 폴링, 화면은 DB 조회, 실패도 이력, TIMEOUT은 GET 재확인 |
